# Storied v0.8 implementation report

This release implements optional declarative rule layers under the [Product Constitution](PRODUCT_CONSTITUTION.md). [The rules guide](RULES.md) explains the author workflow. Deployment and final validation evidence are recorded in [VERIFICATION](VERIFICATION.md).

## 1. Architectural findings

The complete Project snapshot remains the writable authority. `store.mutate` clones and validates it before publishing; the PGlite worker saves JSONB and derived projections in one transaction and waits for durable storage. Boot, import, export, and save share project validation. The existing model ports return text and proposals, never a mutable Project.

Play already has explicit acceptance and branching; Manuscript, Journal, Practice, World Builder, and canon review retain their own working surfaces. No new database, project category, model role, dependency, or execution runtime was necessary for this slice. Ponytail's minimum-necessary principle shaped that decision without removing accepted architecture or validation.

## 2. Constitution and implementation gaps

No conflict prevents this slice. Two accepted architectural commitments remain partly realized: retrieval operates over Project arrays although world-node/edge projections are persisted and indexed; execution-subgraph grouping is mostly metadata although the runner enforces node transitions. Both are retained and documented in ADR 0005. Neither has been silently removed or claimed complete.

Live-table use, simulated participants, reusable content packs, module authoring, and richer source-linked Journal workflows remain future capabilities. Their absence does not create a separate Campaign or Novel project type.

## 3. Durable decisions and roadmap

Added the supplied Product Constitution and accepted [ADR 0005](adr/0005-optional-declarative-rule-layers.md). Updated architecture, extension, project-format, privacy, release, and roadmap documentation. The roadmap keeps medium-agnostic worlds and equally important creative surfaces; TTRPG mechanics are one optional application. Existing ADRs remain intact.

## 4. Exact implemented slice

Settings imports a bounded `.storysystem` JSON file into an inspection dialog. Installation is disabled by default. The author separately enables it for the world and explicitly selects it in Play. With no rules installed or saved, the Play interface has no rules panel.

One reference system, **Small steps**, provides Resolve (0–10, initially 2), Energy (current value out of a fixed capacity of 6), and Reach (Resolve + 2). The author attaches these values to any existing world entity through a validated editor and explicitly saves. Initial suggestions are not persisted before saving. A ruleset can be inspected, exported, disabled, removed, and exactly reinstalled.

The contract permits up to eight installed systems, 16 fields per system, one active system per adventure, and bounded integers. Derived fields only add a constant to a named numeric attribute. Unknown fields, code, arbitrary expressions, indirect dependencies, cycles, invalid references, and invalid bounds are rejected. This is a portable manual mechanical sheet, not action adjudication or simulation.

## 6. Schema and migration

Project format 5 adds `ruleSystems`, defaulting to an empty list, and optional adventure activation and position snapshots. Format 4 migrates additively; previous migrations from formats 1–3 remain supported. Existing adventures and turns are not rewritten to add empty mechanics. Existing worlds open with mechanics off.

Snapshots are anchored to an adventure beginning or accepted turn and to the selected scene event (or unspecified time). New turns copy the parent's snapshots. Branch selection, undo, and redo select those copies. Editing an ancestor cannot rewrite descendants; an old turn without mechanics does not acquire later root state. No new PGlite table or separate authoritative store was added.

## 7. Import, export, and missing systems

`.storysystem` files are previewed before installation and limited to 64 KiB. `.storyworld` retains its existing 32 MiB limit and includes installed definitions, activation, and mechanical snapshots. References, uniqueness, bounds, and matching definitions are checked on import and export, including snapshots whose installation is missing.

Each snapshot embeds its validated definition so saved names, values, and capacities remain readable after removal. Missing systems are not fetched. Inactive systems cannot edit state or calculate derived values. Reinstalling the exact original restores availability; an incompatible replacement requires a future explicit migration and is rejected today. Offline save/reload/export/import use the existing persistence path.

## 8. Authority, canon, and knowledge

Only the explicit author save operation changes mechanical values. It checks project identity, active definition, branch head, scene time, prior snapshot, entity references, and field bounds. Accepted model prose can inherit a copy of prior state but cannot provide replacement mechanics. Rules and values are excluded from model contexts in v0.8; this is not yet a rules-aware storyteller.

Mechanical facets reference world entities without changing narrative fields, canon, memories, beliefs, or character knowledge. Graph edges identify mechanics as non-canon. Canon still requires its existing proposal and author approval flow. Material rule changes invalidate stale AI work through existing revision checks. Actor and timestamp fields record local provenance; they do not authenticate externally edited files.

## 10. Deliberately deferred

No executable plugins, universal expression language, dependency resolution, ruleset composition/upgrades, dice, automatic resource consumption, elapsed-time simulation, D&D implementation, participant simulation, live table, module studio, CRDT sync, or rules-aware model proposal workflow. Existing creative AI and prose-policy behavior is unchanged.

Snapshots currently hold the latest author edit at each position, not an append-only action history. Full definitions and values are copied with branches; large campaigns can reach the whole-world size limit. A future migration can introduce immutable shared definitions or mechanical events when actual usage justifies it. Imported actor labels remain untrusted provenance.

## 11. Smallest next reusable-ruleset step

Have an independent author express a second small system entirely as a `.storysystem` file, then round-trip it between two worlds. Identify one real missing operation from that exercise before expanding the format. Do not add a general language or plugin host preemptively.

## 12. Smallest next TTRPG step

Add one author-initiated bounded check that previews its inputs, records its outcome, and optionally proposes a branch-scoped resource change. Accepting a mechanical outcome must remain separate from promoting a fictional event to canon. This can support a rehearsal, interactive scene, or table encounter in the same world while freeform Play and writing remain first-class.
