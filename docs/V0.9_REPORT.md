# Storied v0.9: reusable rules and recorded checks

Implemented the two approved steps using Ponytail's minimum-necessary approach: a second portable ruleset and one explicit check with a saved outcome and agreed resource cost. [The walkthrough](RULES.md#rehearse-a-crossing) describes the workflow; [ADR 0006](adr/0006-author-initiated-check-receipts.md) records decisions and limits. AI narration of check results is deferred.

## What changed

**Lantern crossing** is an original standalone `.storysystem` file using the existing format 1. It defines Wayfinding, Supplies, and derived Footing. It installs independently in two worlds and is cached for offline download. No rule language, dependency, or provider was added. This proves reuse of the file contract; it is not an external creator usability study.

Play now offers **Make a check** after the author saves an entity's mechanical values. The author chooses a numeric or derived attribute, target, approach, success/setback stakes, and optional resource cost. Review shows the formula and before/after resource balance. **Resolve and record check** draws one local d6, stores its result, and applies the agreed cost together. The attempt cost applies even on a miss and is disclosed before confirmation. Closing review changes nothing; repeated clicks on a stale review cannot reroll or spend twice.

Check history retains source, method version, authored inputs, exact before/after values, die, modifier, total, outcome, and timestamp. Branches inherit copies through the existing `addTurn` behavior. Revisiting a branch, undo/redo, reload, and import select saved results without executing them. Later ancestor edits cannot rewrite existing descendants.

## Architecture, portability, and authority

The complete Project and existing PGlite transaction remain the authority. The shared manual-edit/check guard pins world revision, project, adventure, system, head, time, and prior frame. References, resource sufficiency, numeric bounds, and history capacity are checked before sampling. Browser cryptographic randomness uses bounded rejection sampling; no model or remote dice service is involved.

Project format **5 → 6** adds optional receipt arrays inside mechanical snapshots. Existing rules, enablement, activation, values, and creative records remain unchanged. `.storysystem` stays at format 1. Missing or removed installations preserve readable state and history; import still validates arithmetic, costs, references, original source location, and identical inheritance through parent snapshots.

Checks do not alter prose, canon, knowledge, beliefs, memories, Journal, manuscript text, or practice statistics. Typed graph edges mark their records as non-canon. The model cannot see or mutate check data. No new graph runner, database, plugin runtime, or package dependency was introduced. The accepted but incomplete retrieval/projection and execution-subgraph commitments from ADR 0005 remain documented and intact.

## Limits and next step

The check is a fixed application-owned d6-plus-attribute operation; files do not define check policies. History is capped at 100 receipts per system/time snapshot and the project retains its 32 MiB ceiling. Receipts are copied with snapshots and are not a complete ledger of later manual edits. Saved/pending/error status indicates storage durability. Editable imported provenance is not authenticated or suitable for anti-cheat.

The next approved-design direction is a separate, bounded narration step for an explicitly selected outcome, with permitted world context and author review. General check languages, other dice policies, rule composition/upgrades, simulated parties, sync, executable extensions, and in-app Help remain deferred. The world and every existing creative surface remain first-class.
